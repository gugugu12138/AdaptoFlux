执行结构

观察＋旧状态快照 → 共享特征 → 各动作的独立加权求和 → 同步状态提交 → 互斥许可 → 零输出动作 sink → 图后统一环境推进

44 个特征、88 个冻结系数及乘法、加法均分别展开为真实原生节点。提交节点依赖全部评分，因此所有特征和评分已读取旧状态后才会提交新状态；路由又依赖提交完成 token。这些依赖由适配器显式表达，不依赖节点插入顺序。

共享模式保存四个槽位，提交后两两相同，因此只有两个独立状态通道。随机探索与平局使用外部显式输入的同一个随机数。两个动作 sink 均声明零输出，只有获得许可的 sink 将动作身份写入 StepContext 回执；整张图结束后再统一调用环境推进。

这不是“无适配即可兼容”，也不证明原生核心自动发现副作用依赖、自动消除共享状态写冲突或保证并发安全。本次只核验上述显式提交协议的串行执行。

root 替代 observation，新增 collapse 和 state_commit，共多 2 个节点。多出的 154 条边由 88 条常数调用触发边、4 条旧状态读取边、8 条提交输入边、2 条路由控制输入边和 52 条核验观察边组成。动作 sink 始终没有输出或出边。

常数触发边是为满足原执行器“处理节点必须有前驱”的接口要求；52 条 collapse 边只观察特征、评分、许可与新状态，不决定策略。适配器的端口和元数据检查没有被归为原核心的新能力。

论文可以如何使用

适合用作“通用动作控制结构的可执行实例”：共享特征供不同动作评分复用，跨步状态显式保留，动作副作用通过互斥许可提交。整体模板由人提供，训练主要学习混合系数，飞鸟模型还保留了有限的通用算术特征生长。该核验补充了原生执行证据，未分离模板、生长、状态和优化器各自的训练收益。
